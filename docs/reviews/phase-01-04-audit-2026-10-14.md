## Phase-by-phase assessment

### Phase 01 — Toolchain and executable workspace

**Partly verified; native generation needs a fix.**

The committed lockfile installed successfully into an isolated clean checkout. Shared packages, API, worker scaffold, Next.js production output, and the Android JavaScript/Hermes export compiled. Live web/API health endpoints returned valid HTTP 200 responses.

However, Expo native project generation fails with the current dependency overrides, including in the clean checkout. An older local APK does not verify the current revision. The worker remains a smoke scaffold: its class lifecycle/job tests pass, but `node apps/worker/dist/index.js` prints its startup message and exits immediately. Durable polling, leases, persistence, and retries are later scope; the current README's reference to an established "durable worker" overstates this implementation.

### Phase 02 — Continuous checks and contributor automation

**Quality tooling works; the security gate is failing.**

Lint, formatting, strict types, test suites, secret scanning, and planning validation run successfully. Workflows invoke real scripts and use `contents: read`. Security tests exercise malformed reports, process failures, advisory matching, and exception rejection.

`pnpm audit:deps` currently rejects two high-severity advisories. This is correct enforcement, but it prevents a claim that all contributor gates pass. Hosted CI and remote branch protections still require a configured repository.

### Phase 03 — Platform and integration feasibility

**Useful browser evidence and documented constraints exist; native feasibility remains conditional.**

The real IndexedDB experiment preserved a record across navigation, rolled back an aborted transaction, preserved data during a v1→v2 upgrade, and recovered from a failed v3 upgrade. The duplicate-key experiment emitted a null error result, so that particular evidence is incomplete. Its command-line runner also does not enforce successful experiment results.

The three synthetic model suites pass, but use in-memory abstractions and Node crypto rather than native SQLite, SecureStore, device biometrics, recording, or notifications. The corrective phase report acknowledges these boundaries. External prerequisites are permitted by the Phase 03 acceptance criteria, so these are evidence limits rather than proof that those future integrations are broken.

Current primary documentation supports the recorded best-effort alarm constraints, per-file Drive access, and the distinction between an application-chosen 2 KB credential ceiling and a universal Expo limit. See [Android alarms](https://developer.android.com/develop/background-work/services/alarms), [Drive scopes](https://developers.google.com/workspace/drive/api/guides/api-specific-auth), and [Expo SecureStore](https://docs.expo.dev/versions/latest/sdk/securestore/). The requested SDK 52 SecureStore URL redirected to the current documentation; this does not establish pinned-SDK native behavior.

### Phase 04 — Design tokens and accessible primitives

**Implemented, but not acceptance-complete.**

The web gallery runs. Theme/direction controls, validation-error toggling, keyboard row activation, and dialog opening work. The dialog wraps Shift+Tab from Close to the last action, wraps Tab back to Close, closes with Escape, and restores focus to its opener. Core primary/secondary/action token tests pass.

The findings below show additional contrast, semantics, scaling, and native-control defects. The real-device acceptance gate is also outstanding. The existing `in_progress` status is appropriate; hardware testing is not the only remaining work.

## Required fixes

Priority P1 means an important build/security/acceptance blocker. P2 means a confirmed functionality or verification defect that should be repaired within the affected foundation phase.

### F01 — P1: Android prebuild fails and reports a successful exit

Phase: 01. Sources: [dependency overrides](../../package.json), [mobile scripts](../../apps/mobile/package.json).

Reproduce with `pnpm --filter @daynori/mobile run prebuild` under Node 24.21.0. Both the original checkout and a clean installed checkout report `Cannot read properties of undefined (reading 'extract')` and `Failed to create the native directory`, while `$LASTEXITCODE` is 0. The root build consequently proceeds to `expo export` and exits successfully.

Installed dependency inspection identified the cause: Expo CLI `0.22.28` calls `_tar().default.extract`; the globally overridden `tar@7.5.22` exports `extract` and `__esModule: true` but no default export. Expo's default-import interoperability therefore returns an undefined default.

Fix: evaluate a compatible Expo CLI/toolchain update or a narrowly scoped compatibility patch that uses the patched tar API. Preserve security remediation rather than blindly reverting to a vulnerable tar version. Make native generation failures block validation. Verify a fresh prebuild, generated Gradle files, and an actual development APK build; an Android bundle export alone is insufficient.

### F02 — P1: Dependency security validation fails

Phase: 02. Sources: [audit gate](../../scripts/audit-dependencies.mjs), [pending proposals](../security/pending-exception-proposals.md).

`pnpm audit:deps` exits 1 for `node-forge@1.4.0` ([GHSA-86w9-cpqp-85rv](https://github.com/advisories/GHSA-86w9-cpqp-85rv)) and `braces@3.0.3` ([GHSA-vfj7-8cjw-p6xm](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm)). The advisory pages list no patched versions at review time. These are development-tooling dependency paths; this review did not demonstrate exploitation of a shipped application.

Fix: investigate compatible upstream removal/update or a reviewed patch. If an exception is necessary, complete the repository's human approval, exact-path applicability, expiry, and remediation process. The pending document is not an approval. Retest the gate and its negative tests; keep the current rejection behavior.

### F03 — P1: Dark danger-button text fails the AA contrast target

Phase: 04. Sources: [web Button](../../packages/ui-web/src/Button.tsx), [MobileButton](../../packages/ui-mobile/src/MobileButton.tsx), [tokens](../../packages/design-tokens/src/index.ts).

Switch the web gallery to dark theme. Danger buttons use `#FFFFFF` text on `#F2B8B5`. The rendered style was inspected and the repository's contrast function reports **1.71:1**, below the normal-text **4.5:1** requirement. The native button has the same hardcoded white label. This also affects the dialog's destructive action.

Fix: define a semantic danger-action foreground/background pair per theme and consume it on both platforms. Add coverage for every enabled button variant and theme, including actual rendered colors. [WCAG contrast requirement](https://www.w3.org/TR/WCAG22/#contrast-minimum).

### F04 — P2: Selected-row metadata also fails normal-text contrast

Phase: 04. Sources: [ListRow](../../packages/ui-web/src/ListRow.tsx), [MobileListRow](../../packages/ui-mobile/src/MobileListRow.tsx).

Selected rows change their background to `action.subtle` while retaining `text.muted` for 12 px metadata. Contrast is **3.82:1 in light mode** and **4.13:1 in dark mode**, both below 4.5:1. Disabled controls' contrast exemption does not cover these enabled selected rows.

Fix: select a metadata foreground that passes on every enabled row background, and test default/selected combinations on both platforms.

### F05 — P2: Web row selection uses an unsupported state for its role

Phase: 04. Source: [ListRow](../../packages/ui-web/src/ListRow.tsx).

Activate a row with Enter: selection changes, but the element remains `role="button"` with `aria-selected`, and has no `aria-pressed`. The browser accessibility view did not expose the selected state. The new server-rendered test asserts the same incorrect attribute, so passing that test does not prove the state contract.

Fix: use a coherent selectable-widget pattern, or button/toggle semantics with `aria-pressed` where appropriate. Verify the chosen role/state with a real accessibility check and screen reader. [WAI button semantics](https://www.w3.org/WAI/ARIA/apg/patterns/button/).

### F06 — P2: TextField can reference helper content that is not rendered

Phase: 04. Source: [TextField](../../packages/ui-web/src/TextField.tsx).

Render a field with both `helperText` and `errorMessage`. `aria-describedby` contains `audit-field-helper audit-field-error`, but the helper element is hidden by the `helperText && !errorMessage` condition. A direct server-rendering reproduction returned `helperPresent: false`, `errorPresent: true`.

Fix: either keep the helper visible or construct the description IDs only from rendered elements. Preserve any caller-supplied description IDs deliberately. Test the helper-plus-error combination and recovery back to the valid state.

### F07 — P2: Text-size review does not exercise all primitives; rows truncate content

Phase: 04. Sources: [web gallery](../../apps/web/src/app/page.tsx), [web rows](../../packages/ui-web/src/ListRow.tsx), [native rows](../../packages/ui-mobile/src/MobileListRow.tsx).

The gallery's scale control changes headings and some surrounding text, but primitive buttons/inputs/rows contain fixed pixel font sizes. At the displayed 150% setting, the primary button and input still measured 14 px and 16 px. At 320 px width, row text with `whiteSpace: nowrap`/ellipsis exceeded its visible width; one subtitle measured 383 px inside a 144 px span. Native rows similarly enforce `numberOfLines={1}`.

Fix: make the review setting affect primitive typography, or test actual browser text resizing/zoom and document that distinction. Let important row content wrap or provide an accessible way to see the full content. Make the contrast matrix fit its container or scroll within a labelled region. Retest narrow width and text enlargement; full 200% text resize and 400% browser zoom were not verified here.

### F08 — P2: Native sheet close control misses the documented target size

Phase: 04. Source: [MobileModalSheet](../../packages/ui-mobile/src/MobileModalSheet.tsx).

The close button uses `minHeight: 44` and `minWidth: 44`; the shared mobile target and report promise 48 dp. This is a source-confirmed mismatch, independent of the missing device.

Fix: consume `touchTargets.mobileMin`. During physical QA, additionally verify safe-area insets, keyboard visibility, and access to long/enlarged content; the sheet currently uses a capped, non-scrollable content View. Those layout risks were not confirmed on a device in this review.

### F09 — P2: Native sheet does not respect reduced motion

Phase: 04. Source: [MobileModalSheet](../../packages/ui-mobile/src/MobileModalSheet.tsx).

The sheet always sets `animationType="slide"`; it has no reduced-motion setting or platform accessibility preference handling. Adding a motion token alone does not implement this behavior.

Fix: resolve the OS preference in a platform adapter, support changes to it, and choose an appropriate non-animated presentation when requested. Verify with the Android accessibility setting enabled.

### F10 — P2: Browser experiment results are not a reliable implementation gate

Phases: 03 and 04. Sources: [IndexedDB page](../../tests/spikes/browser/indexeddb-real.html), [IndexedDB runner](../../tests/spikes/browser/run-edge.mjs), [primitive experiment](../../tests/spikes/browser/primitives-real.html).

The IndexedDB helper rejects `tx.error` from `tx.onerror` before a useful error is available. In this real-browser run, the duplicate-key result was `null`, not an observed `ConstraintError`. The runner prints result text but does not assert expected outcomes or fail for an `experiment-error` record; reaching a `done-*` title is not proof of passing checks.

Separately, the newly committed primitive experiment builds its own HTML and event handlers with `document.createElement`, `innerHTML`, and `addEventListener`. Despite its comment about importing compiled primitives, it does not import/mount the actual React components. It can pass even if the real component behavior regresses. Current native unit tests also primarily verify exports and token values, using an incomplete React Native mock rather than mounting interactive controls.

Fix: assert structured experiment outcomes, capture request errors explicitly, and fail on missing/unexpected results or timeouts. Test actual application/components in a real browser and actual native primitives with a meaningful renderer/device workflow. Keep disposable hand-built demonstrations labelled as model/prototype evidence. Root `test:e2e:web` and `test:e2e:android` are currently echo placeholders and provide no journey validation.
